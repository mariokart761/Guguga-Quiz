* 前端：**Nuxt 3 + Vue 3 + Pinia + Tailwind**
* 後端：**FastAPI**
* 後端服務：**同一個 Supabase project**
* DB / Auth / Storage：**Supabase**
* 部署：**Vercel（前端）+ Railway / Render（FastAPI）**

並且以 **「快速上線、自己與朋友使用、同一個 Supabase project 內與既有專案隔離」** 為設計原則。Supabase 支援將自訂 schema 暴露給 Data API，且建議用 custom schema 與 RLS 來控制可存取範圍。`auth.users` 屬於 Auth schema，通常應以自己的業務表去關聯它，而不是直接把業務資料塞進 `auth` schema。Storage 的存取控制則是靠 `storage.objects` 上的 RLS policies。([Supabase][1])

# 1. 專案目標

建立一個可快速上線的線上測驗網站，支援：

* 匯入你現有的試卷 HTML
* 題目含圖片
* 題組題
* 單選 / 複選
* 練習模式 / 模擬考模式
* 錯題本與收藏
* 個人成績統計
* 朋友可共用登入與練習

# 5. 同一個 Supabase project 的隔離策略

## 5.1 Schema 分工

### 既有專案

* 保持原本 schema，不大改

### 新增給測驗專案

* `quiz`：前端與一般 API 可讀寫的正式資料
* `quiz_private`：匯入暫存、管理用 function、內部工具表

Supabase 支援 expose custom schema 給 Data API；同時也建議盡量縮小 exposed schema 範圍，而不是把所有表都放在 `public`。([Supabase][1])

---

## 5.2 Auth 分工

* 共用同一個 Supabase Auth
* 使用 `auth.users` 當身份來源
* 另外建立測驗專案自己的角色表，例如 `quiz.user_roles`
* 業務資料一律關聯 `auth.users(id)`

Supabase 官方建議若要讓使用者資料可被 API 使用，應建立自己的業務表並參照 `auth.users`，再配合 RLS。([Supabase][2])

---

## 5.3 Storage 分工

建立專用 bucket：

* `quiz-assets`：正式題目圖片
* `quiz-imports`：匯入原始 HTML / 附件
* `quiz-temp`：可選，暫存檔

Storage bucket 預設是 private；private bucket 的存取需經 RLS / signed URL 控制。Storage 的 metadata 在 `storage` schema 中，且 SQL 層面應視為唯讀，檔案操作走 API。([Supabase][3])

---

# 6. Supabase schema 說明

## 6.1 `quiz` schema

用途：**正式題庫與前台使用資料**

包含：

* 題庫
* 作答紀錄
* 收藏
* 錯題本
* 角色
* 供前端查詢的 view / RPC

這個 schema 會加入 Supabase 的 exposed schemas，前端透過 Supabase client 讀寫。因為它是 exposed schema，所有表都必須啟用 RLS。([Supabase][1])

---

## 6.2 `quiz_private` schema

用途：**內部處理，不直接給前端碰**

包含：

* 匯入任務
* 原始 HTML 暫存
* 解析中間結果
* 管理用 helper function
* 批次重建索引 / 統計 function

原則：

* 不 expose 給 Data API
* 只讓 FastAPI 的 service role 或安全函式使用

---

## 6.3 `auth` schema

用途：**Supabase Auth 系統管理**

* `auth.users`
* session / token 等 auth 相關資料

原則：

* 不直接拿來放業務資料
* 你的題庫資料只用 FK 連到 `auth.users.id`

---

## 6.4 `storage` schema

用途：**Storage metadata**

* `storage.buckets`
* `storage.objects`

原則：

* 透過 Storage API 存取檔案
* 權限寫在 `storage.objects` RLS policy

---

# 9. RLS 設計原則

因為 `quiz` 是 exposed schema，所有表都開 RLS。Supabase 明確建議 exposed schema 的表必須啟用 RLS。([Supabase][4])

## 9.1 一般使用者可讀

* `quiz.papers`：已發布試卷
* `quiz.question_groups`：已發布試卷中的題組
* `quiz.questions`：已發布試卷中的題目
* `quiz.question_options`：已發布試卷中的選項

## 9.2 一般使用者只可讀寫自己

* `quiz.attempts`
* `quiz.attempt_answers`
* `quiz.bookmarks`
* `quiz.wrong_question_stats`

## 9.3 只有 quiz admin 可讀寫

* 題庫編輯
* 匯入任務
* 題目發布
* 題目刪除
* Storage 寫入 `quiz-assets`
* Storage 讀寫 `quiz-imports`

# 10. Storage bucket 規劃

## `quiz-assets`

用途：

* 題目圖片
* 題組附圖

建議：

* private bucket
* 前端用 signed URL 或 authenticated 存取

## `quiz-imports`

用途：

* 上傳原始 HTML
* 匯入用附檔

建議：

* private bucket
* 只有 admin 能上傳與讀取

Storage 的存取權限由 `storage.objects` RLS policy 控制；private bucket 下載也受權限約束。([Supabase][5])

# 11. API 設計草案

## 11.1 前端直接用 Supabase client

適合：

* 登入
* 讀題
* 新增作答
* 收藏
* 查自己的歷史紀錄

### 例子

* `quiz.papers` 查詢已發布試卷
* `quiz.questions` 依 paper 查題目
* `quiz.attempts` 建立作答
* `quiz.attempt_answers` 寫入答案

---

## 11.2 FastAPI 負責管理與匯入

適合：

* 上傳 HTML 並建立匯入任務
* 解析 HTML
* 拉取外部圖片並上傳 Storage
* 批次建立題目 / 題組 / 選項
* 題庫管理後台 API

原因：

* 匯入與整理屬高權限操作
* 不適合直接從前端做
* 可使用 service role 或直連 DB

# 12. 匯入流程

```text
1. Admin 上傳 HTML 到 quiz-imports
2. 建立 quiz_private.import_jobs
3. FastAPI 讀取 HTML
4. 解析 paper / group / question / option / answer / image
5. 圖片下載後上傳至 quiz-assets
6. 寫入 quiz_private.import_raw_items 供預覽
7. Admin 檢查結果
8. 發布到 quiz.papers / question_groups / questions / question_options
```

# 15. 最後定案建議

這個版本，我會建議直接這樣落地：

## 專案定案

* **同一個 Supabase project**
* **新增 `quiz` schema**
* **新增 `quiz_private` schema**
* **新增 `quiz-assets` / `quiz-imports` buckets**
* **Nuxt 前端只碰 `quiz`**
* **FastAPI 管匯入與後台**
* **所有 exposed 表都開 RLS**

這樣有幾個好處：

* 不用多付一個 Supabase project 的 compute
* 與既有專案隔離清楚
* 邏輯簡單，適合 side project 快速上線
* 未來若真的要拆出獨立 project，搬移也容易
